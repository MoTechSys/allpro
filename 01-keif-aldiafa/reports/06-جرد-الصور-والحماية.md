## 2) تحليل أسماء الملفات واشتقاق `alt`

### المصدر البرمجي المفحوص
- `src/lib/imageCatalog.ts`

### كيف يشتق النظام `alt` من اسم الملف
من دالة `filenameToText`:
1. يأخذ اسم الملف بدون الامتداد.
2. يقسم على `-` و`_`.
3. يحذف المقاطع الرقمية البحتة مثل `1`, `2`.
4. يقتطع إلى أول `7` كلمات لتفادي الحشو.
5. يضيف وسم فئة عربي من `CATEGORY_AR` ثم النص المشتق.

صيغة الناتج:

```text
<تصنيف عربي> — <كلمات وصفية من اسم الملف>
```

### تقييم التسمية
- نعم، الأسماء لاتينية وصفية بدرجة جيدة (`saudi`, `hospitality`, `coffee`, `jeddah`...).
- النمط الغالب `kebab-case` متوافق جداً مع الاشتقاق الآلي للـ`alt`.
- لا يوجد مسارات بأحرف غير ASCII في أسماء الملفات (فحص عملي عبر `grep` على المسارات).

### ملاحظة جودة
- بعض الأسماء طويلة جداً وقد تحمل تكرار كلمات SEO؛ الكود يخفف ذلك بقصّها إلى 7 كلمات.

## 5) صور OG وخرائط الموقع

### الملفات المفحوصة
- `src/app/image-sitemap.xml/route.ts`
- `src/app/sitemap.ts`
- `src/app/sitemap_index.xml/route.ts`
- `public/og-*.jpg`
- `src/components/SEO.tsx` و`src/app/page.tsx` و`src/app/layout.tsx`

### نتائج الفحص

#### وجود ملفات OG

```bash
find public -maxdepth 1 -type f -name 'og-*.jpg'
file public/og-cover-v2.jpg public/og-image.jpg
```

```text
public/og-cover-v2.jpg
public/og-image.jpg

public/og-cover-v2.jpg: ... 1200x630 ...
public/og-image.jpg:    ... 1200x630 ...
```

#### هل كل صفحة لها OG مخصصة؟
- **لا**. الموجود عملياً صورة OG أساسية واحدة مستخدمة فعلياً على مستوى الميتاداتا: `og-cover-v2.jpg`.
- دالة `generatePageMetadata` في `src/components/SEO.tsx` تضبط `ogImage` افتراضياً إلى `https://keifaldiafa.com/og-cover-v2.jpg`.
- لا توجد تمريرات `ogImage:` مخصصة للصفحات عند الاستدعاء (فحص `rg` لم يجد تخصيصاً).
- الصفحة الرئيسية تعيد تعريف OG لكنها أيضاً تستخدم `og-cover-v2.jpg`.

#### وضع خرائط الموقع
- `image-sitemap.xml` مبني آلياً من كل الصور القابلة للفهرسة عبر `getImagesByPage()` في `imageCatalog`.
- `sitemap_index.xml` يربط `sitemap.xml` + `image-sitemap.xml`.
- `robots.ts` يعلن خرائط الموقع الثلاثة.

**الاستنتاج:** فهرسة الصور موجودة فنياً، لكن استراتيجية OG ليست مخصصة لكل صفحة حالياً.

## 6) حماية الملكية: الآلية الحالية وما ينقص

### المصدر المفحوص
- `src/components/ProtectedImage.tsx`
- `src/app/legal/page.tsx`
- `src/lib/schema.ts`

### آلية الحماية الحالية (عملياً)
1. تعطيل قائمة الزر الأيمن (`onContextMenu` + `preventDefault`).
2. تعطيل السحب (`draggable={false}`).
3. طبقة Overlay شفافة فوق الصورة (`absolute inset-0`).
4. علامة مائية بصرية (SVG) تظهر فقط عند `showWatermark={true}`.

### نقاط مهمة
- `showWatermark` افتراضه `false`، إذن ليست كل الصور مائية تلقائياً.
- الحماية الحالية **واجهة أمامية فقط**؛ لا تمنع screenshot أو حفظ الصورة من الشبكة عند كشف الرابط.

### IPTC / EXIF (فحص فعلي)

#### أوامر منفذة

```bash
exiftool -r -q -q -if '$EXIF:All or $IPTC:All' -filename public/images | grep -c '^File Name'
exiftool public/images/equipment/royal-golden-dallah-coffee-pot-saudi-hospitality.webp | rg -n 'IPTC|EXIF|Copyright|Artist|Creator|Credit|Description|Title|XP|License|Date'
```

#### نتائج
- عدد الملفات التي تحمل EXIF/IPTC حسب الشرط: **`31`** ملف.
- عينة من ملف حقيقي أظهرت وجود `WebP Flags: XMP, EXIF` و`Creator Tool: Adobe Photoshop...`.
- لا تظهر بصمة حقوق واضحة/موحّدة على كل الصور (مثل `Copyright Notice`, `Licensor`, `Usage Terms`) في كامل المكتبة.

### صفحة الشروط/الحقوق
- موجودة: `src/app/legal/page.tsx` وتتضمن منع الاستخدام بدون إذن + قنوات طلب ترخيص.
- موجود كذلك ترابط حقوقي جيد في `ImageObject` داخل `src/lib/schema.ts` (`license`, `acquireLicensePage`, `copyrightNotice`).

## 7) خطة تنفيذ مقترحة

## أ) خط إنتاج الضغط (WebP/AVIF متعدد المقاسات)

### الهدف
- تخفيض وزن النقل وتحسين LCP/CLS بدون كسر SEO.

### الخطة
1. اعتماد مصدر رئيسي Master (مثلاً JPEG/PNG عالية الجودة) خارج `public/images`.
2. توليد نسخ متعددة المقاسات لكل أصل: `480`, `768`, `1200`, `1600`.
3. لكل مقاس: إخراج `AVIF` (جودة ~45-55) + `WebP` (جودة ~62-70).
4. الاحتفاظ بنسخة fallback عند الحاجة.
5. فرض حد جودة تلقائي: أي ملف يتجاوز `250KB` يعاد ضغطه أو يعاد قصّه.
6. توليد Manifest JSON للأبعاد/الأوزان لكل صورة لاستخدامه في المراجعة والنشر.

### خطوة تشغيل مقترحة
- سكربت CI يفشل البناء إذا:
  - صورة جديدة > `250KB` بلا استثناء.
  - عدم وجود نسخة `avif` أو `webp` للمقاسات الإلزامية.

## ب) خطة الفهرسة (Image SEO)

### الموجود الآن (جيد)
- `image-sitemap.xml` مولّد آلياً من الكتالوج الحقيقي.
- `alt` مشتق آلياً بشكل وصفي.
- `max-image-preview: large` موجود في metadata (layout + مولد SEO).
- `ImageObject` حاضر في `generateImageGallerySchema` مع `license/acquireLicensePage`.

### المطلوب لرفع الجودة
1. ربط `generateImageGallerySchema` بجميع الصفحات التي تعرض صوراً وليس صفحات محددة فقط.
2. توحيد `primaryImageOfPage` لكل صفحة هبوط أساسية.
3. تخصيص OG لكل صفحة أساسية (`/services`, `/offerings`, `/portfolio`, `/locations`...) مع صور 1200×630 مختلفة.
4. تقليل طول أسماء الملفات المستقبلية (5–9 كلمات كحد أعلى) لتقليل ضجيج ALT.
5. إضافة تدقيق CI للتأكد أن كل صورة داخلية لها سياق صفحة واضح في الكتالوج.

## ج) خطة حماية الملكية (Watermark + IPTC + DMCA)

### طبقة 1: العلامة المائية
1. تحويل سياسة `showWatermark` إلى مفعّلة افتراضياً في صور المعارض.
2. دعم نسختين watermark:
   - خفيفة للواجهة.
   - أقوى للنسخ المعرّضة للسرقة (المعرض/البورتفوليو).
3. تثبيت موضع متسق + عشوائية طفيفة اختيارية لمقاومة القص.

### طبقة 2: بيانات الملكية داخل الملف (IPTC/XMP)
1. كتابة حقول موحدة على كل الصور المنشورة:
   - `CopyrightNotice`
   - `Creator` / `Credit`
   - `WebStatement` = `/legal`
   - `LicensorURL` = `/contact`
2. إعادة تصدير كل المكتبة مرة واحدة + فحص آلي بعد التصدير.

### طبقة 3: إنفاذ قانوني وتشغيلي
1. إضافة فقرة DMCA/بلاغ انتهاك صريحة في صفحة `legal` (نموذج بلاغ + SLA استجابة).
2. تجهيز قالب Notice-and-Takedown جاهز للإرسال.
3. أرشفة بصمة كل أصل (hash + تاريخ نشر + رابط الصفحة) كدليل ملكية.
4. مراقبة دورية للنسخ غير المصرح به (Reverse Image Search مجدول شهرياً).

## الخلاصة التنفيذية
- الوضع الحالي قوي في **تنظيم الصور والفهرسة التقنية** (Image Sitemap + ALT + Schema جزئي).
- أبرز فجوتين الآن:
  1. **عدم تخصيص OG لكل صفحة** (صورة واحدة شبه موحّدة).
  2. **الحماية الحقوقية غير مكتملة داخل الملفات** (EXIF/XMP موجود في جزء فقط وبلا سياسة موحدة).
- الأولوية العملية التالية: خط إنتاج صور موحد + OG مخصص + توحيد IPTC/XMP + فقرة DMCA تشغيلية.
